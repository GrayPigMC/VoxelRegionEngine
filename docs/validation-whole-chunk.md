# 整区块执行与 GTLCore 验证记录

日期：2026-10-28。原始日志、生成的测试世界、精确启动参数和各次制品保留在本地 `.local/runs/`；本页记录可审查的结果与限制，不包含玩家存档或证据。先前的球壳基线见 [历史记录](validation-0.1.0.md)。

## 验证范围

普通 Forge 对比使用 Minecraft 1.20.1、Forge 47.3.7、Java 17.0.19、单个逻辑 CPU、3 GiB 堆、零玩家的独立服务端。Core 验证使用标准 Forge 47.4.16、两个逻辑 CPU、4 GiB 堆、真实 GTCEu/AE/FTB 等依赖；没有复制完整玩家整合包的 KubeJS 配方脚本，不能称为完整整合包验收。全部并行重任务总计不超过四个逻辑 CPU，机器并非独占。

计时取完整 `MinecraftServer.tickServer`，包含 Forge END、探针和服务端工作。时间窗不包含停服保存，也不等于所有异步队列的独立 CPU 用量。原生 `forge tps` 不能替代这个口径。

## R2000 暴露的问题

`production-whole-r2000-candidate01` 开启生成，采用默认 64 个在途区块，在提交后约 89.716 秒的观测末尾实际提交并保存确认 **534 个区块**，改变 16,257,077 格，批量提交 4,352 个 section。完整 R2000 尚未完成，49,542 个几何候选不算完成数。爆心 124 个标记位于一个区块，0.646 秒/5 ticks 清理完毕，1/1 原生保存镜像检查通过；它不是密集样本的 9 区块夹具。

完整 tick 窗口包含 1,511 个样本，平均 30.22 ms、P95 68.73 ms、P99 163.33 ms、最大 **14,270.94 ms**。日志确有约 14.2 秒落后警告，不能用平均值掩盖它。

外部光照安装仍为 0，回退 534 次。代码检查发现整块路径在处理原生余项前就调用光照策略，策略又以“存在原生余项”直接拒绝。爆心最终保存像只有空气和基岩，说明至少这个区块最终符合证明域，原来的调用时序却使它失去机会。后续修正必须在完整修改后重新证明，同时保留边界修订、原生修复与保存依赖；本节数字保留为修正前基线。

`release-whole03`（SHA-256 `2cf9f9f5d42e6719c7e169b1bdbb60666baf653c633142e19fcd368fc7f0b5a5`）将光照证明移到原生余项之后，并在 palette 含不支持的条目时核对实际使用的状态 ID。`setBlock(AIR)` 留下的未使用旧条目不会再被误当作仍存在的流体或发光方块。原生回退仍处理真实残留、邻区块缺失及失效证明。

针对长 tick 的额外 JFR 运行使用 JDK `profile`，最多保留 128 MiB，并在退出时保存。采样有开销，不能把其耗时和先前无采样数字当作严格倍速对照。旧制品复现 17.954 秒峰值；对应窗口的 1,080 个服务端线程栈样本定位到 `ChestBlock.onRemove → Containers.dropContents → RandomizableContainerBlockEntity.unpackLootTable → ExplorationMapFunction → findNearestMapStructure`。删除未打开的战利品箱时，拦截掉落实体并没有阻止生成宝藏地图及其结构搜索。旧无 JFR 的 14.27 秒峰内，28 次 young GC 总停顿约 135 ms，不能解释主体耗时。原始栈与时间关联证据保留在本地各自 run 中。

## 实体 API 发布检查（2026-10-29）

新增独立 `ForgeEntityOperations`，默认包含玩家和未加载的已保存实体。它按实体位置的连续几何选择，分帧处理原生实体存储，支持状态和取消；正常击杀与直接移除分别保留各自语义。`APPLIED` 是动作完成，不是磁盘同步确认，详见 [对接文档](entity-operations.md)。既有地形任务不会自动改为杀死玩家。

`entity-api-native02` 使用标准 Forge 1.20.1 / 47.3.7、Java 17、4 个逻辑 CPU、4 GiB 堆和正式重映射的适配器。仓库中的 `EntityOperationScenario` 由独立本地探针驱动，115 个场景 tick 完成全部断言：

- 加载中的生物和物品分别进入原生死亡/移除流程；范围外实体保留。
- 默认包含玩家、显式排除玩家均生效。玩家使用可受伤的 Forge `FakePlayer` 夹具验证原生健康/死亡路径，未将死亡玩家对象直接移除；这不是完整联网玩家重生测试。
- 通过 Forge 原生伤害事件拒绝击杀的生物仍存活，`surviving` 如实计数。
- 两个球的交集在区块边界上相切，没有选中任何方块中心，但准确移除切点上的实体并保留外侧实体。
- 排队后立即取消的请求不处理目标。
- 真实区块卸载、实体对象退役及新对象重载后，`LOADED_ONLY` 没有改变已保存目标；默认保存范围随后将其杀死，并保留同区块选区外的实体。
- 再次真实卸载后的 `DISCARD` 不加载地形，重载确认目标已消失而选区外实体仍在。
- 对远处从未生成的空区域提交实体操作，原生地形存储前后读回均不存在该区块。

第一轮 `entity-api-native01` 已通过加载实体、玩家、边界和取消阶段，但因“正常击杀后地形仍未加载”的过强断言而失败，原结果保留。Forge 的生物死亡姿态更新会经过尺寸刷新与 `setPosRaw`，后者对已加入世界的实体调用 `level.getChunk(...)`；因此第二轮分别验证 KILL 的原生死亡/持久化行为与 DISCARD 的无地形加载路径，没有跳过原生回调来迎合测试。
