# 全局光照接管

Forge 集成的全局光照组件覆盖客户端和服务端，不限于区域清理任务。普通方块与流体变化、发光方块变化、区块生成、加载和卸载均经过该组件。方块光与天空光继续通过 Minecraft 的光照查询接口和原版网络包提供给渲染器。

## 组件与许可

采用 Starlight Forge 的 Minecraft 1.20 系列实现作为基础，固定上游提交 `6585522a74113317be3ed06bbb17b5305d3075c0`，并适配 Forge 1.20.1。上游代码、修改和来源保存在 `third_party/starlight-forge/`，沿用 LGPL-3.0。编译产物是独立的 `vre-starlight-forge-1.20.1-1.1.2-vre.jar`，由宿主或测试模组通过 JarJar 内嵌；不要求玩家额外安装 Starlight。

VRE 的纯 Java 算法与空间任务调度器继续采用 MPL-2.0。源码同步工具将两种许可的组件分别同步到宿主的 `vre-engine/`、`vre-forge/` 和 `vre-starlight/`，不将第三方组件改标为 MPL。

## 调度与数据所有权

光照层挂在实际区块上；工作线程使用独立计算上下文。相互影响的区块范围按读写依赖排序，互不影响的范围可以并行。并行不意味着邻区块依赖不存在，也不意味着可以同时覆盖同一光照层。

普通变化先合并同一区块的更新，再交给空间调度器。区域清理在整个区块的方块提交和必要回调完成后请求重新计算光照。保存与网络提交等待实际光照完成凭据，不能用“队列已提交”代替完成。

旧版区域算法通过原版光照存储写入结果；全局组件启用时，这组原版存储 Mixin 不加载。两套数据发布方式不能混用。保留旧引擎仅用于隔离对照测试：启动 JVM 时设置 `-Dvre.globalLighting=false`，需要重新启动，不支持世界运行中切换存储实现。

服务端工作线程数可在启动时用 `-Dvre.globalLighting.threads=N` 指定，范围为 1–64；默认取可用处理器数减一，限制在 1–8。更多线程不保证更快：重叠光照范围必须排序，区块生成、网络和其他模组还会竞争 CPU。客户端沿用同步 Starlight 计算路径。不要同时安装另一份 Starlight 或其他替换相同光照实现的模组。

## 存档与渲染兼容验证

Starlight 保留标准 `BlockLight` 和 `SkyLight` 数据，并附带自己的格式版本和空层状态。为让不认识这些标记的引擎重新计算，它将原版 `isLightOn` 标为 false；因此不能仅凭这个字段判定光照保存失败。

光影与泛光验证必须同时检查服务端和客户端光照数值，以及真正渲染的画面。隐藏窗口创建成功、OpenGL 初始化成功、没有抛异常，都不能单独证明渲染兼容。

当前目标环境为 Oculus、Embeddium、Helian-MMCO 光影及 GTLCore 泛光，覆盖以下配置：

- 光影关闭，GTLCore 泛光关闭。
- 光影关闭，GTLCore 泛光 AUTO。
- Helian 开启，光影泛光关闭，GTLCore 泛光关闭。
- Helian 开启，光影泛光开启，GTLCore 泛光关闭。
- Helian 开启，光影泛光开启，GTLCore 泛光 AUTO / LabPBR。

验证场景包含光源增加和移除、跨区块移动、玻璃与半砖遮挡、天窗开闭、区块卸载重载和保存重启。图像测试先验证有效 framebuffer 和场景标记变化，再比较画面；不能把黑帧当作通过。具体通过范围以对应构建的验证记录为准。

这些场景不代表所有动态方块光学均已验证。实际整合包的静态审查覆盖了 Forge 发光与遮挡回调、Embeddium 光照读取和 Oculus 渲染接口；依赖方块实体的动态伪装仍受模组自身访问上下文与并发行为限制。例如 TravelAnchors 的部分伪装回调在原有后台光照线程中也可能取不到方块实体，不能将其描述为本组件已修复或全面兼容。

### 2026-10-30 验证记录

本地候选构建 release44 的正式 GTLCore JAR 在实际 77 模组整合包中验证，使用隐藏的真实客户端与集成服务端，不操控鼠标。渲染环境为 Oculus 1.8.0、Embeddium 0.3.31、Helian-MMCO 1.1.0 和 GTLCore 泛光。

- 上述五种配置通过八阶段光照与画面检查；每阶段分别核对服务端和客户端的 221,184 个光照值，并与冻结的参考结果比较。
- 真实 framebuffer 通过场景标记 A/B/A 变化检查。本地泛光和 Helian 泛光开关均产生可测画面变化，不以“配置已开启”代替实际效果。
- 独立 PBR 正控制使用原生不发光的磨制闪长岩：两侧公共方块光均为零，AUTO 模式确认规则命中和材质上传后，固定图像区域平均亮度由 25.91 增至 217.85（0–255）。这将 GTLCore PBR 效果与光影对萤石的原生识别分开验证。
- Helian + GTLCore AUTO 配置正常退出保存后，重新启动并在任何场景写入之前核对双端光照数据，通过。夜间增加、移除光源也通过数值检查与实际画面变化检查。
- 便携算法完整回归的 19 组检查通过；实际整合包批量方块写入、混合保护与完整光照完成屏障检查通过。

同一 JAR、两个逻辑 CPU、8 GiB 堆、相同几何的 867 个已生成区块的单次配对测试中，关闭全局组件耗时 33.885 秒，启用后为 22.293 秒（计时清理阶段，排除启动和预生成）。这不代表普遍性能承诺：启用后的该轮 tick p95 从 77.11 ms 增至 181.67 ms，最大 tick 从 3580.92 ms 降至 769 ms；两轮预生成工作量也不完全一致，实际改变的方块数相差 641（约 0.0027%），并非字节完全相同的地形输入。插桩显示区域光照仍有相邻重建范围重复扫描成本，世界生成则主要耗在地形与矿物计算。不能将清理提速外推为所有世界生成场景均提速。

另以普通 `level.setBlock` 增删光源测试日常更新，未使用区域批量重建：固定已加载的 6×6 区块，2 轮预热后测量 16×256 次变更。原生总写入到光照完成累计 310.390 ms，全局组件为 191.027 ms（本次减少 38.46%）；其中方块写入分别为 45.693 / 49.345 ms，写完到实际完成凭据分别为 264.696 / 141.682 ms。18 轮双层光照完整哈希逐轮相同，每进程独立核对 2,412,544 个方块光值。启动、预热和结果验证不计入耗时。原生轮仍有后台平坦世界区块状态推进，两轮均无 FEATURES 请求或 GT 矿物采样增量；因此它是实际整合包固定负载的单次对照，不是隔离计算内核或普遍性能保证。
