# 全局光照实现与验证状态

此前直接导入的第三方光照源码、专用构建脚本和独立嵌套库已经移除。当前交付恢复为 engine 与 Forge adapter 两份库。没有通过重命名、换包名或修改署名保留被移除的实现；独立替代实现只能以通用算法和接口契约为参考。

旧 release44 使用的是已移除的实现。它的正确性、光影/泛光兼容性和性能结果仅说明那个冻结构建，不能证明当前替代实现已经通过验证。本页不把旧测试数字作为新实现成绩。

## 实现范围

新的计算器位于 `org.voxelregion.forge.lighting`，只依赖 Minecraft 的 `LightChunkGetter`、`BlockGetter` 等接口。原生队列、存档与网络框架保留；光照计算由 VRE 的增量/全量求解和矩形任务合并处理，区域清理通过整列重建桥接。新实现不需要额外 AT，也没有独立第三方 JAR。

数值核心 `GlobalLightField` 独立于 Minecraft：直接天光按竖列处理，只把直射区与阴影区的有效交界加入传播；普通方块变更在缓存有效时增量更新光场，缓存缺失或整列重建时执行全量求解。相邻脏列合并成矩形任务，携带一整圈区块的计算边界后交给工作线程。工作线程只读脱离世界的光学数据，不调用方块或世界对象。完成的光照图像一次发布，数值求解不使用原版传播器。

完整采集分为准备和数据组装两个阶段。光照所属线程读取区块与调色板，执行全部上下文光学回调和成对形状判断，再冻结独立的截面计划。上下文回调得到的标量值在本次采集中封成新的不可变 `OpticalTile`，包括防御性复制、值域校验与来源摘要；这些值不进入跨任务的静态缓存。工作线程创建自己的 Builder，解码静态调色板、批量复制已冻结的光学块和组装快照，随后执行原有数值求解。不会把 Domain、活区块或世界对象交给工作线程，静态形状引用也不会在工作线程调用。所有同时保留的截面输入另计内存预约，发布前继续复核完整邻域的身份和地形修订。诊断中的 capture 时间包含两个阶段的累计耗时，不能把转移到工作线程的时间当成被消除的成本。

形状遮挡仅保存实际有内容的 4096 格不可变页，并批量复制最终面掩码；不再分配第二份整域遮挡数组后逐格回填。跨页相邻面的两侧都保留，向下遮挡仍参与天空直射来源上界。静态形状使用已缓存的实际索引，冻结计划只保留标量光学块。适配层也不再写入由非零不透明度重复推导的 stop 位；完整计算和增量更新都已检查该不透明度。纯算法仍支持不透明度为零但显式阻断直射的独立 stop，不能把这个能力一并删除。

### 算法参考与独立实现

参考的是算法与边界条件，未复制下列项目的源码、位打包方式或类结构：

- [Starlight 的算法说明](https://github.com/PaperMC/Starlight/blob/6585522a74113317be3ed06bbb17b5305d3075c0/TECHNICAL_DETAILS.md)：区分撤光与补光，直射天光只从有用的交界传播。这里从不可变旧光场推导递减依赖：旧邻居值等于旧来源减去边的衰减时，才可能需要撤掉其贡献；随后依据新遮挡、保留光源恢复结果。方块光和天光分别失效，避免一次发光变化重算全部天空光。
- [Lucis 的传播实现](https://github.com/Team-Argentum/Lucis/tree/49b09d593a2b96f98425288bc3887ee5f2908630/src/main/java/dev/denismasterherobrine/lucis/light)：参考按亮度分层传播和批量变更的思路。当前补光使用独立实现的 16 级桶队列，先传播较强的贡献；条目携带入队时的亮度，过期条目不会再次传播。队列使用有界分页存储，满载时把未处理位置记录在两层独立的位集中，稍后按当前亮度补回，不能因达到容量而丢失工作。撤光全部完成后才开始补光。
- [ScalableLux 的调度实现](https://github.com/RelativityMC/ScalableLux/tree/77c290c4c84be1c87d006bc8221e5361d98e0c9a/src/main/java/ca/spottedleaf/starlight/common/thread)：参考对空间依赖的显式约束。这里采用独立的只读光学快照、无重叠输出矩形、可重叠只读边界和版本校验，计算完成后由光照所属队列统一发布。

全量初始化把直接天光表示为连续区间，批量填入 15，传播队列只接收有效交界和真实发光源。完整采集仍须取得计算域的真实光学数据；使用来源摘要的输入可以省去数值初始化阶段的重复整域扫描，无摘要输入继续精确扫描。增量更新缩小天光竖列扫描范围，并沿旧光场的依赖撤光，但仍需要复制结果数组，不能把整个调用的成本说成只与修改数量有关。

快照验证同时记录最高发光或向下遮挡位置，初始化不再逐格遍历其上方已知无源的空气。向下扫描只检查尚未找到最高遮挡的竖列，不因少数开口列而继续遍历其他列中埋在地下的遮挡。各列直射起点不变；所有列共同暴露在天空中的上方区间连续填写，其余起伏部分保留各列的精确区间。两项优化不裁短世界，也不忽略光从低处向上扩散。

混合截面的静态光学解码使用独立、有界的内容缓存。每次仍重新捕获不可变调色板，缓存键比较全部有序方块状态、存储格式及压缩索引内容；哈希相同不足以命中。仅原生已证明静态的材质进入缓存，依赖世界或位置的发光、形状继续逐点采样；邻接面遮挡在组合截面后重新计算。缓存上限 64 MiB，不保留世界、区块或整域光场；全空和光学均匀截面继续走更短的直接路径。

全量采样之前先识别完整高度内只有原生空气和基岩的区域。证明覆盖整个采样矩形和邻域后，使用自有 `OpenRegionLighting`：基岩所在高度带精确计算，证明为空气的上部用均匀层表示。高处基岩会扩大计算带，不能一律假定只保留底部 16 格。只发布内缩一整圈的区块，外围结果不作为世界光照；流体、发光物、半砖或其他材料走通用计算。两条计算路径共用版本校验、不可变发布和完成凭据。

输出矩形精确覆盖实际脏列，不因网格对齐扩大输出。若已有缓存光场覆盖多个输出，计算可以复用同一光场，只发布需要的列。缓存还记录各列当前已发布图像的身份，避免“数值没变”错误地跳过已被另一份光场覆盖的列。区块身份、光学修改版本和地形修订不符时重新捕获。缺少必要邻区块的任务等待真实数据到达，不把未知邻居当空气，也不确认尚未发布的任务已经完成。

区块启用光照的代际与地形修改代际分开记录。新可用性代际只有在整个缓存域的区块身份及已知地形修订都未改变、且没有同时发生光学修改时才能复用；缺乏修订证据的 ProtoChunk 仍保守重算。这份证据随缓存跨批次保存，不能只检查当前一批的通知。Open 结果的纯发布不会额外淘汰整个相交邻域；实际修改代际、区块卸载及图像 token 仍阻止复用过期结果。普通 checkBlock 增量保留原生事件完整性契约，未在事件批次出现的已知地形修订漂移会拒绝缓存。

缓存未命中的全量任务可进一步共用一个计算矩形，但保留原始输出列表。只有新计算矩形连同一圈边界全部包含在原采样范围的并集中、采样面积严格减少且数值及宿主捕获预算允许时才合并。中间孔洞仅参与读取，不发布、不增加生成或持有区块的要求。该局部规划有明确尺寸上限，不对整批任务做无界两两搜索；它是有界启发式，不保证最优分组。

分页队列最多分配 256 页，每页 256 个整数；小计算域按需要进一步收紧上限。快照、规划器共用有溢出检查的工作内存估算，包含队列和溢出位集。该估算限制单个数值任务，不能替代整个游戏的内存预算。算法正确性与整合包中的捕获、调度和发布耗时分开验证。

宿主另有全进程共享工作预算，将采样临时数组与数值计算同时计入；额度持续占用到实际计算和发布结束。形状材料使用按需分页引用，不因一个形状方块分配整域材质数组。堆空间紧张时淘汰数值缓存并缩小任务，瞬时可用堆只作为缩容信号，不能把等待 GC 的垃圾误判为永久失败。重捕获先结束已有批次再申请新额度，避免持有本批额度等待本批释放。预算限制本实现拥有的工作数据，不承诺限制其他模组回调内部的任意分配。

完整光学采集通过 `GlobalLightField.Snapshot.Builder` 的受控写入与批量复制方法进行。标量、范围和 checked-row 在写入时校验；`OpticalTile` 先复制并校验两个通道，再以不可变对象共享，复制其行或完整截面不再重复校验值域。静态块可来自内容缓存，上下文块则每次重新生成。旧 raw-row 入口仍触发最终整域校验，公开 Snapshot 数组构造器仍执行防御性复制。`consume()` 根据最终内容确定来源上界并移交内部缓冲区，不再复制第二份整域数组。Builder 不暴露数组，强制构造线程归属；成功或失败的 consume 都永久关闭写入入口并释放其引用。宿主暂保留原有保守内存预算，未因减少分配而同时放大并发准入。

两种光值都遵循 Minecraft 的 0–15 标量语义。普通扩散每经过一条边至少衰减 1，一圈 16 格地形边界足以计算裁剪后的内区；直接天光从世界顶部单独求证，屋顶变化可能影响下面整列。半砖等形状由原生相邻面的遮挡关系捕获为有向边，改面即使没有改变该位置自身亮度，也要撤销旧的出边贡献。光影软阴影、彩色光和泛光仍由渲染器处理。

真实服务端世界负责计算；客户端维护服务端发送的权威光照层，支持原生稀疏天空光的向上继承。客户端缺少邻区块时不会自行求解并覆盖服务器数据。GuideME、LDLib 等虚拟场景保留各自的原生光照契约，不向 `Level` 或所有区块子类添加新的抽象方法。

调度按有限批次合并：第一个原生队列标记到达时封闭当时已接收的批次，等这一批全部前置操作就绪后计算。后来的批次不能越过尚未就绪的早期批次；队列标记本身立即返回，不占着原生调度器等待计算。这样既减少过早拆批，也保留前置修改、数值发布和完成回调的顺序。

接管的光照队列在异常路径也发送队列 ACK，并复位调度标志。ACK 仅放行队列，不表示光照成功。致命计算失败停止该引擎后续计算与成功 POST，相关 future 明确异常完成，未发布列的保存标志失效；正在使用的输入等活动调用退出后才释放。普通单个 future 取消不升级为整个引擎的致命错误。该故障协议不承担故障后自动重启光照引擎的职责。

整列清理在写入前取得光照读邻域的共享票据。修改会影响相邻输出列，而相邻输出还要读取一圈地形，因此持有两圈最低 `FEATURES` 状态的地形；不为这些读区块请求 FULL 或 ticking。只有当前可见 holder 与票据就绪后才开始写入，待光照、保存和发包都结束才释放。禁止生成时先核实缺失地形是否已经保存，无法证明时在写入前暂停。一次发布的缺失邻域只影响相关凭据，不会让同一批中远处已经成功发布的列一起失败。

旧有区域光照路径保留用于 `-Dvre.globalLighting=false` 的重启对照。不能在世界运行中切换实现。吞吐量必须以同一构建、同一环境的测量为准。

完整光学块还可在采集时合并两种来源索引：每竖列最高直射阻断起点、每 16 格是否可能含发光源。不可变光学块复用自身摘要，整块复制只合并 256 列；初始化读取确定的直射起点，仅扫描可能发光的行。重复覆盖后，过高候选必须依据最终不透明度、显式 stop 和向下面重新校正。无索引的公开数组输入、增量派生快照仍使用原精确扫描。索引内存另计入工作及缓存预算，每次检查索引字和光源格也消耗分步额度。

索引按冻结输入的表达选择。Builder 的三参数构造器默认不建立索引，四参数构造器可显式启用。当前分阶段采集把上下文值也冻结成当次独有的光学块，因此均匀块、静态块和上下文块都可批量组装并启用索引；不会再为这条上下文路径逐格维护整域摘要。源码保留旧标量计划的无索引兼容分支，同步采集也默认不启用索引。两种初始化方式计算相同光场，不改变精度。准备计数 `optical_prepared_indexed`、`optical_prepared_scan` 反映实际选择；它们不是完成或发布计数。微基准不能代替真实整合包中的覆盖比例和总耗时。

## 接入与升级

宿主继续使用 Forge adapter 的公开区域 API。构建时应先执行 clean，移除旧生成类、refmap、Mixin 配置、AT 和独立光照 JAR；不能从旧 build 目录补入缺少的文件。源码同步工具会根据旧清单逐文件删除已移除模块及其专用 Gradle 脚本。

新的全局光照实现保持 Minecraft 标准的光照查询、区块与网络接口。GuideME 使用原有接口渲染场景，不需要实现额外的即时区块查询接口，也不需要安装针对被移除组件的兼容补丁。

旧组件保存的区块带有 `isLightOn=false`；新实现不会解释其私有版本标记，而由正常区块 LIGHT 流程重新计算。新结果使用标准光照 NBT。保存完全为零的天空光层时保留显式零值，避免重载后把它当成缺省天空光继承。

## 本次必须重新验证的行为

- 普通世界的方块、流体、发光状态变化，以及区域批量清理；不应依赖先运行测试命令才能更新光照。
- 增光、减光、天空直射与遮挡，半砖、玻璃、保留流体及跨区块边界；与独立参考值核对。
- 待处理和执行中的任务代际、空间写入排他、完成凭据、失败结算、区块卸载及停服。
- 保存后重启，在任何场景重写前读取光照值，防止保存了未完成或失效的光照。
- 实际整合包的 GuideME、Embeddium、Oculus、Helian 光影及 GTLCore 泛光；同时核对服务端/客户端数值与真实画面，不能只以成功启动或无异常作为通过。
- 绑定新 JAR 哈希的耗时、吞吐、tick 尾延迟和 CPU 配额。新测量不得继承旧实现的性能结论。

依赖方块实体的动态发光或伪装回调需要分别检查线程上下文；通用算法的数学正确性不能替代模组兼容性验证。通过范围只以新构建对应的实际结果为准。

## 独立实现的已验证范围

当前本地候选为 release71（Core SHA-256 `f36e306f0e666c9610bd3ccb4262e43fced076891bc68c4cc4931035eb1ce0ac`）。编译及嵌套库检查通过；纯算法门槛包含 31 组已有 portable 测试及新增来源索引双模式测试，共 32 组。release71 的数值核心与已验证的候选 70 相同，沿用这份冻结源码的纯算法结果；上下文输入表达的改变另由新宿主 fixture 和下面两轮真实整合包测试验证。
