# 批量执行与一致性契约

算法库和 Forge 适配器分开发布。几何、掩码、传播索引不访问 Minecraft 世界；Forge 适配器负责取得世界数据、检查权限和提交。测试 mod 只提供物品与命令。GTLCore 尚未接入。

## 从中心推进

新任务默认先处理爆心附近的一格半径，再逐圈向外处理互不重叠的球壳。首个候选区块是爆心区块；后续每圈按 Region/Chunk 顺序推进。圈宽可配置，默认 32 格。一圈的已提交光照、存档和同步工作收尾后，才推进下一圈。

这是分层批处理，不承诺每个方块都严格按距离排序。需要最大吞吐时可选择 `AS_FAST_AS_POSSIBLE`；其访问顺序侧重存储局部性。两种模式的几何结果相同。旧任务持久化的波面格式保持原样，不能以新圈宽或新起步规则解释旧进度。

默认 `generate=false` 只修改处理时已经加载的区块。未加载区块会记为排除项，旧任务以后不会因它被加载而补炸。`generate=true` 才允许读取或正常生成整个请求范围。状态必须显示排除数量；加载范围受限的任务完成不等于整个球体都已清除。

## 提交路径

完整覆盖的静态区段先检查 Palette、精确非空气计数、权限、修订号和宿主观察器支持。能证明安全时，一次替换状态容器，保留生物群系；同一区块内可批量提交多个区段。它不执行 4096 次 `setBlock`。

边界使用连续 Y 行段生成局部掩码，只枚举被选中的格子。完整区段的快速证明接受原版三种空气、受支持的静态不透明方块，以及允许清除的原版水源和流水。含方块实体、POI、特殊回调、岩浆、含水固体或无法证明安全的状态，走原生精确路径。领地禁止的区块和完整阴影直接跳过；仅因 Palette 含受保护状态而拒绝批量写入时，仍逐格检查。未知宿主观察器没有通过聚合通知契约时，不能假定裸换容器安全。

批量写入后一次重建四种 FULL 高度图和天光源列，清理被完全删除区段的定时刻，并请求原生光照更新。严格不透明区段主要检查外表面；含空气或水的区段还要处理内部天光源与旧阴影的接口，防止旧亮度阻止新路径传播。不得伪造 `isLightCorrect`，也不得借用生成光照票据作为普通重照明完成证明。

默认不生成方块战利品。原生写入作用域内，还会阻止删除格同步产生的新物品实体，因此箱子的 `onRemove` 仍完整执行，但不会吐出海量库存。此作用域不删除已有实体，不影响其他坐标、线程或作用域结束后的正常掉落；Mod 延迟生成的额外掉落需要其宿主适配配合。

## 权限与快照

`canDestroy`、`blocksPropagation` 和区块修改权限分别决定删除、阴影和授权。默认传播为 `NONE`。开启 `AXIS_6`、`AXIS_26` 或 `RAYCAST_REFINED` 后，先只读捕获全范围的阻挡事实；删除尚未开始。静态标签负责阻挡判定，原生修订号和持续的变更订阅验证捕获期间没有混入不同时间的区块状态。

宏体素边长支持 4、8、16。相邻盒只有几何并集不扩大、且传播方向条件允许时才合并，不能为了减少盒数改变阴影定义。源盒、数字修订号和策略信息以独立不可变文件持久化，然后在一个有界后台工作线程中建立索引。后台任务不持有可变区块、方块实体或世界对象。

缺少区块、变更跟踪失效、捕获期间修改或单次捕获超出上限会显式暂停；全局额度暂时被其他工作占用时则等待。未知空间不能当成没有阻挡物。冻结后的旧任务恢复读取原文件并验证哈希，不能重新读取已炸空的世界来计算阴影。

同维度中范围相交、且至少一个启用了传播的任务按接受顺序执行。后一个任务在前一个结束并确认全部收尾后才开始捕获；前一个暂停时也保持顺序，用户可以取消它。这样快照对应轮到该任务执行后的稳定世界，不把多次爆炸误称为共享同一批初始快照。纯几何任务仍可共用预算并在不同区块并行推进。

默认 32 MiB 是操作元数据、捕获、排队/运行中的索引任务和已驻留遮挡索引共用的估计额度。取消后台工作不会立即退还仍被线程持有的数据额度。它不是 JVM 总堆限制；Minecraft 区块、NBT 解码和网络缓冲仍各有独立的有界工作窗口。

## 未生成区块

已有存档区块始终使用原生读取，不能拿新空区块覆盖。安全快捷路径目前针对可证明的原版平坦生成器：原生存储确认无数据、没有已有或进行中的 ChunkHolder、绑定原生新建的 ProtoChunk，且没有结构、特征或未知生成扩展。

快捷路径在原生 NOISE 阶段保留真实配置中的受保护层，跳过其余层的无意义生成写入。保留写入上限为 4096 格，且必须实际跳过至少一层，否则走普通生成，避免把大量地形工作搬到主线程。其后仍经过原生生成状态、光照和 FULL 发布流程。NOISE 提交前重新核对权限、规则与世界边界；证据变化回退正常生成。噪声地形或未知 Mod 生成器继续正常生成再清除，这是明确的兼容路径，不是伪造 FULL NBT。

## 完成、暂停和恢复

每个原生区块保存镜像同时包含地形、操作 UUID、圈数、精确游标和修改修订号。原生写入前记录 pending，成功返回后才推进游标。外部回调失败、重入保存和无法判定的中断不会被当作已经完成。

完成确认分别等待原生光照、实际 terrain/POI store futures、存储同步，以及需要的区块包提交。包的预算按实际序列化字节乘追踪玩家数计算；无人追踪时不用发包。网络提交不等于远程客户端已经渲染或确认收到。

同一圈内已经写完的区块进入有界收尾队列，随后可以处理下一区块。正在写入和等待收尾的区块共用票据上限，默认全服务器最多 8 个；收到确认前继续持有区块修改权。进入下一圈或标记完成前，必须等这一圈全部确认。状态分别提供准备、加载、写入、光照、保存和发包的实际待办计数，不拿半径比例冒充完成百分比。

取消与暂停也要收完此前已经提交的工作。已持久化的取消记录优先于旧 SavedData；完成标记会阻止旧波面重放到新建筑上。没有可验证的同镜像回执时保守暂停，而不是重新发起一次爆炸。实体伤害没有同镜像恢复证据时也不自动重放。

## 性能测量

使用 `MinecraftServer.tickServer` 入口与返回之间的完整时间。原版 `averageTickTime`/`forge tps` 的采样发生在 Forge END 事件之前，会漏算 END 中的区域操作，不能单独用作本引擎的性能结论。

比较时固定种子、生成和加载状态、CPU、堆大小、保护策略、几何和预算。分别记录准备、主线程提交、光照尾部、存档完成、实际包字节与总任务时间。小型后端采样证明的是该路径的成本；加载范围有限的 R2000 样本不能证明整个 R2000 地形已经处理完毕。

最终通过的用例和数值以独立的验证记录为准；本文件描述实现契约，不替代运行结果。
